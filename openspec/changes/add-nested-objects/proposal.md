# Proposal

## Why

Records are flat, so a customer cannot carry an `address` with its own `city` and `postcode`, and a reference cannot read a value from inside such a group. This is the structural half of making records look real, and the two changes that follow (text building and realistic data) both depend on it. It also rewrites how the engine identifies fields, which is risky today because nothing pins the values the engine currently produces.

This is the first of three changes that replace the single `add-rich-field-types` draft. Order: `add-nested-objects`, then `add-text-and-custom-types`, then `add-realistic-data`.

## What Changes

- **A safety net first.** A golden-output test records the exact bytes generated today for a fixed spec and seed, and a CI workflow runs the tests and linter on every push and pull request. Both land before any engine change, so "existing specs keep their values" is checked, not assumed.
- **Nested objects.** A new `object` field type holds its own `fields`, to a depth of ten levels.
- **Robust validation of structure.** Nesting deeper than the limit, including a YAML document that contains itself through an anchor, is reported as a validation problem. No input may crash the validator.
- **References into nested fields.** `$customer.address.city`, or `field: address.city` in the long form. A reference to an object copies the whole object, and a reference may read through an object that was itself copied.
- **Export.** JSON and JSON Lines write objects nested. CSV flattens them into one column per leaf, named by path (`address.city`), with an `output.csv_separator` option for loaders that reject dots in column names.
- **Python API.** Records may hold nested mappings, each independent of every other record, and the column paths of an entity are available to callers.

Out of scope here: patterns, templates, hidden fields, uniqueness and custom types (next change); built-in names, emails, phones, addresses and Faker (the change after); lists inside a record.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `simulation-spec`: new `object` field type; a nesting limit; `output.csv_separator`; references may name a nested path in both forms.
- `data-generation`: how objects are generated, how references read nested fields and copied objects, and stability of nested values.
- `file-export`: nested output in JSON and JSON Lines, flattened columns in CSV, and the separator option.
- `python-api`: nested records, independence of copied objects, and access to an entity's column paths.

## Impact

- **Prerequisite**: `feature/add-spec-shorthands` must be merged into `develop` first, and this branch recut from `develop`. The deltas here modify requirements that only exist once that change's specs are on `develop`, and stacking on an unmerged branch that will be squash-merged produces conflicts.
- **Code**: `spec.py` (object model, field shapes, depth limit, nested reference checks), `generators.py` and `engine.py` (path-keyed streams, nested rows, nested reference reads), `exporters.py` and `api.py` (flattening, column paths).
- **Tooling**: `tests/golden/` with recorded output, and `.github/workflows/ci.yml`.
- **Compatibility**: additive. For any existing spec and seed the generated bytes are unchanged, enforced by the golden test.
- **Performance**: throughput for flat entities must stay within 15% of the figure measured immediately before this change, on the same machine.
- **Dependencies**: none added.
